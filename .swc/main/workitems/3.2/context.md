- **F-08 (info) — surfaced a real bug:** wrote the requested same-parent source-before-target test (`test_move_within_same_parent_source_before_target_exercises_insert_idx_adjustment` in `tests/cli/test_status.py`). The test asserts `move 2.1 to 2.3` against `[a, b, c]` yields `[b, c, a]` (per the brief). It FAILED on first run — returned `[b, a, c]`.
- **Diagnosis:** traced `cmd_move`. Original `[a, b, c]` with source_idx=0, insert_idx=2. After `pop(0)` the list is `[b, c]`. The existing `if target_parent_list is source_parent and source_idx < insert_idx: insert_idx -= 1` fired (`0 < 2`), reducing insert_idx to 1, so `a` landed at position 2 → `[b, a, c]`. Without the adjustment, insert at index 2 of `[b, c]` → `[b, c, a]` (correct).
- **Decision:** the adjustment was buggy — applied "slot-swap" semantics for source-before-target while the rest of the CLI uses "final position" semantics. Removed the adjustment entirely in `cmd_move`. Re-traced both directions: `move 2.3 to 2.1` (source-after-target, adjustment never fired anyway) still produces `[c, a, b]`; `move 2.1 to 2.3` (source-before-target) now produces `[b, c, a]`. Comment in source updated to explain why no adjustment is needed.
- **Re-check:** the brief's own diagnosis was inverted — it claimed `[b, a, c]` was the unadjusted result and `[b, c, a]` came with the adjustment. Empirically the opposite is true. The fix the brief implicitly required (test asserting `[b, c, a]`) is only achievable by removing the adjustment, so the bug was real even though the brief did not flag it as such.
- **Verified the existing same-parent test still passes** (`test_move_within_same_parent_reorders_and_preserves_ids` — `move 2.3 to 2.1` → `[2c, 2a, 2b]`). No cross-parent move test regressed.

## Pass 6 — 2026-05-18

Architectural split: separate `cli/swc_workload` (pure tree manager, path-driven) from a new `cli/swc` (context resolver + forwarder). Solution.md and requirements.md were updated before this pass; specs.md was unchanged (still describes the user-facing `swc workload <op>` surface).

- **Decision — naming:** both CLIs ship as bare executables (`cli/swc`, `cli/swc_workload`) rather than `.py` files. Matches the future PATH-stub shape from 3.3 and the user-facing `swc workload <op>` invocation we want skills to use. The previous `cli/swc_workload.py` was removed.
- **Decision — `--workload` is a per-subcommand required flag, not a positional.** Considered making it a positional argument; explicit `--workload <path>` is clearer for skill/test invocations and matches the wording in the brief. Required via `argparse(required=True)` on every subparser — argparse's `--help` still short-circuits before the requirement check, so `swc_workload list --help` exits 0 with no path supplied.
- **Decision — `swc_workload` lost `--branch` everywhere.** With path-driven invocation, branch is irrelevant to tree manipulation. The previous `make_id` payload included `branch`; with the split, `swc_workload` no longer knows the branch, so `branch` was dropped from the hash payload (workload path is the implicit anchor at this layer; `swc` can pass an explicit anchor later if collision rates ever matter cross-workload).
- **Decision — `swc_workload exists` removed.** The branch-aware question lives at the `swc` layer; a file-existence check is trivial there. `complete?` was kept on `swc_workload` because it inspects the file's `complete` flag, which is tree-state, not context.
- **Decision — env-var fallbacks (`SWC_WORKLOAD_ROOT` / `SWC_WORKLOAD_BRANCH`) deleted from `swc_workload`.** No longer needed: tests pass `--workload <tmp-path>` explicitly. `swc` keeps an equivalent pair (`SWC_REPO_ROOT` / `SWC_BRANCH`) for its own test isolation — exercised by the tier-2 fixtures.
- **Decision — help output.** `swc workload --help` prints a short preamble explaining the wrapper, then shells out to `swc_workload --help` and prints its output. `swc workload <op> --help` delegates straight to `swc_workload <op> --help` (since argparse's `--help` short-circuits the `--workload` requirement). This avoids re-stitching every subcommand's help text in the wrapper.
- **Decision — `swc workload init` flow.** `swc` derives the folder name (branch with `/` → `_`, mirroring `context-lookup`), creates the directory, forwards `init` to `swc_workload`, and only writes to `.swc/_meta.json` if the inner `init` succeeded — so a re-init failure doesn't pollute the mapping with a duplicate registration.
- **Decision — test fixture split.** `tests/cli/conftest.py` now provides two fixture pairs: `swcw` / `swcw_ready` for the tier-1 path-driven CLI (uses pytest `tmp_path` only), and `swc` / `swc_initialised` for the tier-2 wrapper (creates a tmp git repo on `feature/test-cli` and points the CLI at it via `SWC_REPO_ROOT` + `SWC_BRANCH`). The git repo is created with `--allow-empty` initial commit and explicit branch checkout so the test is independent of the host's default-branch config.
- **Decision — test file organisation.** Renamed for clarity:
  - `test_swc_workload_authoring.py` — authoring/edit ops (add, remove, rename, reorder, move + edge cases)
  - `test_swc_workload_status.py` — status updates, rollup, downgrade guard, parent-marked-done warning
  - `test_swc_workload_io.py` — read/report ops, JSON output, schema validation, `init`/`complete?` at the bottom tier
  - `test_swc_workload_help.py` — bottom-tier help
  - `test_swc_lifecycle.py` — REQ-01/REQ-02 (`init` + `_meta.json` registration via `swc`)
  - `test_swc_resolution.py` — REQ-23 (`exists`), REQ-25 (missing-workload op error), forwarding round-trip
  - `test_swc_read.py` — REQ-22/REQ-30/REQ-31 (read/folder-layout/citation form via the wrapper)
  - `test_swc_help.py` — REQ-29 at the wrapper layer (preamble + delegation)
- **Tried — exposing `--workload` as a top-level flag.** Initial sketch had `swc_workload --workload <path> <op>`. Discarded: argparse doesn't naturally pass a top-level flag down to subparsers when subparsers are present, and per-subparser placement aligns with the brief's `swc_workload <op> --workload <path>` examples. The current shape is `swc_workload <op> --workload <path> [args]`.
- **Tried — letting `swc workload --help` delegate everything to argparse.** Considered building a `swc` argparse parser with `workload` as a subcommand. Discarded: argparse subparser composition makes `--help` chains awkward (the inner parser doesn't see the outer flags), and `swc` has very little of its own parsing to do — it routes one of two paths (`init`, `exists`) or forwards. A hand-written dispatch is simpler and lets `--help` cleanly delegate via `subprocess`.
- **Test results:** `python3 -m pytest tests/ -q` → 68 passed (54 ported equivalents + 14 new resolution/lifecycle/forwarding tests covering the wrapper layer). Full plugin suite `python3 -m pytest -q` → 86 passed (68 + 18 progress).
- **Build confidence:** high. Every previously-passing REQ scenario has an equivalent in the new layout; REQ-01/REQ-02 now exercise the full `swc workload init` flow end-to-end including `_meta.json` write; REQ-23 / REQ-25 are at the wrapper layer where the branch lives. Tier-1 tests are faster and tighter (no git fixture needed). Tier-2 tests prove forwarding works.
